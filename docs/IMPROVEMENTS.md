## 2026-10-20 — 기획 & 개선안 제안팀 실무 분석 (MoaCook, 코드 근거 포함)
> 위 섹션들의 `.omc/` 나열 항목은 소스가 아닌 OMC 런타임 상태 파일이라 개선 대상이 아님. 아래는 실제 소스(`server/utils`, `app/composables`) 기준.

### P0 — 즉시 조치 (저비용·고효과)
- **`.omc/`를 `.gitignore`에 추가**: `.gitignore`에 `.omc` 항목이 없어 세션/락/tmp 파일 182개가 계속 untracked로 잡힘. 이 때문에 정적 분석 입력과 이 문서가 `.omc/...: 점검 필요` 같은 무의미한 줄로 부풀어 있음(문서 135KB, 737줄). `.omc/skills/**`만 예외로 두면 됨.
- **자동 생성된 노이즈 섹션 정리**: `docs/IMPROVEMENTS.md` 3~735줄은 전부 동일 문구의 파일 나열. 위 gitignore 반영 후 삭제하고, 생성기가 자기 자신(`docs/IMPROVEMENTS.md`)을 변경 파일로 다시 나열하는 루프(736~737줄)도 끊을 것.

### P1 — 성능 병목
- **목록 조회가 요청마다 전체 테이블 `select=*`** (`server/utils/recipeRepository.ts:138`, `server/utils/recipeStore.ts:60-64`): 목록 화면은 `toRecipeSummary`(`recipeStore.ts:106`)로 재료·조리 단계를 버리는데, DB에서는 `ingredients`/`steps` JSONB까지 모두 가져옴. 레시피가 늘수록 서버리스 함수 ↔ Supabase 전송량이 선형 증가. 개선: 요약용 `listSummaries()`를 두고 `select=id,name,image,description,category,difficulty,cooking_time`만 조회. 단, 검색이 재료 이름까지 보므로(`recipeSearch.ts:8`) 재료 검색을 유지하려면 `ingredients`는 남기거나 DB 쪽 검색으로 이동 필요.
- **정렬 이중 수행** (`recipeRepository.ts:138` `order=created_at.asc` + `recipeStore.ts:63` `sort(localeCompare)`): Supabase가 이미 정렬해 주는데 서버에서 다시 정렬. 로컬 파일 저장소(`recipeRepository.ts:39-43`)만 정렬이 필요하므로 정렬을 로컬 저장소 쪽으로 내리면 Supabase 경로에서 O(n log n) 제거.
- **`updateRecipe`가 `findRecipe` → `save`로 왕복 2회, 그 안에서 `ensureSeeded` 재확인** (`recipeStore.ts:83-94`): 존재 확인을 `PATCH ... id=eq.X`(+`return=representation`) 한 번으로 줄일 수 있음. 관리자 전용이라 우선순위는 낮음.
- **서버 캐시 헤더 부재 여부 점검**: `server/api/recipes/index.get.ts`에 `Cache-Control`/`defineCachedEventHandler`(예: `swr` 60초) 적용 여부 확인 필요. 읽기 위주 서비스라 Vercel CDN 캐시 + 저장·수정·삭제 시 무효화로 Supabase 호출 대부분을 제거할 수 있음. (이번 범위에서 파일은 열어보지 않았으므로 미확인 항목)
- **콜드 스타트 시 시드 순차 처리** (`recipeStore.ts:26-44`): `for` 루프 안에서 레시피마다 `get` → `save`를 직렬 `await`. 버전이 올라간 첫 요청은 시드 N개 × 왕복 지연만큼 느려지고 그동안 모든 목록 요청이 `seeding` 프라미스에 막힘. 개선: `list()` 한 번으로 기존 id 집합을 만들고 신규 레시피는 배열 POST 한 번(PostgREST bulk insert)으로 처리.

### P2 — 리팩토링 포인트
- **`useRecipeList.findSummary` 선형 탐색** (`app/composables/useRecipeList.ts:19-25`): 캐시된 모든 필터 조합의 목록을 순회하며 `find`. 필터 조합이 쌓일수록 느려지고 같은 레시피가 여러 목록에 중복 저장됨. `Record<id, RecipeSummary>` 정규화 맵을 따로 두면 O(1). 규모가 작아 지금은 문제 아님(YAGNI), 조합 캐시 수가 늘면 적용.
- **`useState` 캐시 무제한 증가** (`useRecipeList.ts:15`): 검색어마다 키가 생겨 SSR 페이로드(`__NUXT_DATA__`)로 직렬화될 수 있음. 서버에서는 캐시를 채우지 않거나 클라이언트 전용 상태로 두는지 확인하고, 키 개수 상한(예: 최근 10개)을 고려.
- **`RecipeRow` ↔ `Recipe` 수동 매핑 이중 관리** (`recipeRepository.ts:86-119`): 컬럼이 늘 때마다 `toRow`/`fromRow`/`supabase/schema.sql` 세 곳을 동시에 고쳐야 함. 필드 누락은 타입 검사로 일부 잡히지만 optional 필드(`youtube_query`)는 조용히 빠질 수 있으므로 왕복 변환 단위 테스트 1개 추가 권장.
- **저장소 인터페이스에 `update` 의미 부재** (`recipeRepository.ts:9-10` `save`가 upsert): `updateRecipe`가 존재 확인을 별도로 해야 하는 원인. `get`+`save` 대신 `update(id, content): Promise<Recipe | undefined>`를 두면 레이스(확인 후 삭제된 레시피를 다시 살리는 문제)도 함께 해결됨.
- **`createRecipe`의 `ensureSeeded` 선행 호출** (`recipeStore.ts:74`): 신규 등록은 시드와 무관하지만 첫 요청이 시드 완료를 기다림. 순서 보장이 필요한 이유(시드가 id를 덮어쓰지 않음)가 없다면 제거 가능. 확인 후 판단.

### P3 — 아키텍처 개선안
- **시드 로직을 요청 경로에서 분리**: 현재 모든 읽기/쓰기가 `ensureSeeded()`(`recipeStore.ts:17`)를 거침. 서버리스는 인스턴스마다 모듈 변수 `seeding`이 따로라 인스턴스 수만큼 `getSeedVersion` 조회가 반복되고, 동시 콜드 스타트 시 여러 인스턴스가 같은 시드를 중복 실행할 수 있음(upsert라 데이터는 안전하지만 낭비). 대안: Supabase 마이그레이션 SQL 또는 Nitro 플러그인(배포 시 1회)로 이동하고 요청 경로에서는 제거.
- **검색을 DB로 이동 (장기)**: 현재는 전체 목록을 가져와 메모리에서 필터(`recipeSearch.ts:13-19`). 레시피가 수백 건을 넘으면 Postgres `pg_trgm`/`ilike` + 인덱스로 서버 필터링하고 페이지네이션(`limit/offset`)을 도입. 현재 규모에서는 과설계이므로 레시피 수 기준(예: 300건)을 정해 두고 그때 전환.
- **이미지 최적화**: 업로드 이미지는 Supabase Storage 원본 그대로 노출. 목록 카드용 썸네일은 Supabase 이미지 변환(`/render/image`) 또는 Vercel Image Optimization 경유 + `loading="lazy"`·`width/height` 지정 여부 점검(CLS/LCP 개선). 컴포넌트 파일은 이번 범위에서 열어보지 않음.

### 추가 아이디어 (기능)
- 재료 기반 역검색("냉장고 재료로 찾기"): 이미 `ingredients` 이름을 검색하므로 다중 재료 AND 매칭 + 일치율 정렬을 `recipeSearch.ts`에 추가하면 소규모 변경으로 핵심 가치(오늘 뭐 해먹지) 강화.
- 인분 조절: 재료 분량 숫자 파싱이 필요하므로 데이터 모델(`RecipeIngredient`)에 `amount:number`/`unit` 분리 필요 — 기존 레시피 마이그레이션 비용이 있어 우선순위는 낮음.
- 즐겨찾기/최근 본 레시피: 로그인 없이 `localStorage`로 충분(서버 변경 없음).

> 한계: 이번 분석은 `server/utils/recipeRepository.ts`, `recipeStore.ts`, `recipeSearch.ts`, `app/composables/*`만 열어 본 결과이며, API 핸들러·페이지·컴포넌트는 읽지 않아 해당 항목은 "확인 필요"로 표시함.
